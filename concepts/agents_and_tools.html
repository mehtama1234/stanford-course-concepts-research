Agents, Retrieval, And Tools

A loop where a language model takes an action, sees the result, then decides what to do next.

What real-world problem is this about?

You ask a librarian a question about a book published yesterday. The librarian cannot answer from memory alone. She has to walk to the shelf, check the catalog, pull down a reference, read the new information, then come back and answer you. Her knowledge is not enough; she needs to act and observe.

Why does this problem exist?

A language model's weights contain facts frozen at training time. Real tasks demand current weather, database lookups, running code, or changing the world. No weights can store 'today's date' or 'the stock price right now.' So the model must step outside itself, observe, and adjust. This is not a choice — it is a logical necessity.

What is the mathematical idea underneath?

A model maintains a state (what it knows so far). At step t, it chooses an action a_t (a tool to call or query to send) based on the state. The action produces an observation o_t (the result). The state updates: state_{t+1} = state_t + a_t + o_t. The model then uses the new state to choose the next action a_{t+1}. This feedback loop, not a single forward pass, drives the system. Each action narrows the space of possible next states, creating a search through possibilities.

Why is this concept important?

This loop connects models to live data (search APIs, weather, stock prices), computation (running Python code, solving equations), databases, and user actions. Without it, every task is frozen in time. With it, a model can answer 'what is today's news?' or 'solve this algebra problem step by step' or 'book me a flight' by composing external tools.

What breaks without it?

The model cannot access information it was not trained on. It cannot verify facts. It cannot perform actions that change the world. A weather model cannot check real conditions. A coding assistant cannot run tests. A booking agent cannot actually purchase tickets. Every answer becomes a guess from stale knowledge.

Naive Starting Point

A beginner sees the problem and thinks: I can just make the model smarter by giving it more data at training time, or I can hardcode specific rules for each task. Hardcode rules for 'fetch weather' here, rules for 'search the web' there.

Why the Simple Approach Fails

Hardcoding rules fails because the tasks are infinite and overlap in unexpected ways. 'Fetch weather for a city' needs the city name, which might be hidden in an earlier sentence. The rule engine sprawls into thousands of if-then statements and still misses edge cases. It does not learn; it only gets more brittle.

The Mathematical Object

The agent loop can be represented as a decision table or a sequence of (state, action, observation) triples. The state is a running transcript of text (including previous results). The action is a choice from a discrete set: 'call search', 'run Python', 'query database', 'respond to user'. The observation is the text result returned by that tool. You can inspect this sequence, trace where it went wrong, and measure how much context the model actually used.

The Operation

Start with the user's query as the initial state. The model reads the state and outputs the name of a tool and an input for that tool. Execute that tool and append its result to the state. Repeat: the model reads the extended state, chooses the next tool, and so on. Stop when the model outputs a final answer instead of a tool name.

Worked Mini-Example

User asks: 'What is the highest-grossing film of 2025?' Step 1: State is just the question. Model chooses action 'search for highest-grossing 2025 films'. Observation comes back: 'Top results: Dune Messiah, Avatar 4, etc.' Step 2: State now includes the search results. Model chooses 'fetch details on Dune Messiah box office'. Observation: '$1.8B worldwide.' Step 3: State includes both results. Model outputs the final answer: 'Dune Messiah, $1.8B.' The loop halts because the model output an answer, not a tool call.

What the Lectures Emphasize

The Stanford CME295 agentic LLM lecture frames the shift from a standalone model to a model inside a system. The model was 'on its own'; now it can 'interact with outside systems through RAG, tool calling, and agents.' This is the move from prediction to closed-loop interaction. The lecture does not teach how to build tools; it teaches why a loop—not a bigger model—solves the real-world problem.

Common Misunderstanding

People think an agent is a bigger model or a clever prompt. The crucial change is architectural: the model is now wrapped in a loop, not a monolith. It does not decide everything at once. It decides one action, learns the result, and decides again. This loop creates new failure modes: bad tool results, misuse of tools, hallucinated tool outputs, and cascading errors that a simple prompt never faced.

How to Recognize This in a New Paper or Model

In a paper or system, look for closed-loop structure: the model makes a choice, an external process executes, new information feeds back, and the model chooses again. You will see it called 'agent', 'retrieval-augmented', 'tool-using', 'planning loop', or 'environment interaction'. They are all the same core: a model that observes, acts, and updates its state repeatedly.

Connected Concepts

In Deep RL (CS224R), an agent also observes state, chooses an action, and receives a reward. In Diffusion (CME296), sampling involves a loop where the model refines an image step by step, observing the current noisy image and choosing how to denoise. The pattern of action-observation-update appears everywhere, whether in language, robotics, or images.
