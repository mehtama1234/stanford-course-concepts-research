Agents, Retrieval, And Tools

A cycle where a language model (a program trained to predict text) takes one action at a time, gets a result, and uses that result to decide the next action.

What real-world problem is this about?

You ask a librarian a question about a book released yesterday. The librarian cannot answer from memory alone; she never read it. She walks to the shelf, checks the catalog, pulls the book down, reads the new information, returns, and answers you. Her training (what she studied before) is not enough. She needs to move through the world and gather information.

Why does this problem exist?

A language model learns patterns by reading millions of examples during training. The patterns it learns are frozen once training stops. Real tasks require knowledge that did not exist during training: today's weather, current stock prices, what is inside a specific database, or the ability to change the world by booking a flight or sending an email. No amount of pattern recognition can know 'today's date' or 'what happened five minutes ago.' The model must step outside itself, retrieve live information, run code, or take real actions, then use those results to answer correctly.

What is the mathematical idea underneath?

The model maintains a record of what it knows so far (starting with just the user's question). At each step t, it reads this record and outputs the name of a tool to call and what to ask that tool for. The tool executes and produces a result (observation o_t). The model adds this result to its record. At step t+1, it reads the expanded record and chooses the next tool. The record grows: record_{t+1} = record_t + [tool call] + [tool result]. This repeated cycle—read record, choose action, execute, add result—creates a chain that walks toward the answer. Each new result guides the next decision, narrowing down possibilities.

Why is this concept important?

This cycle connects a language model to external systems: weather APIs, Google searches, databases, Python interpreters, email systems, flight-booking APIs, calculators. Without the cycle, a model can only guess based on its training data, which is old. With it, a model can answer 'What is the weather in San Francisco right now?' by calling a weather API, or 'Solve 47 times 89' by running Python, or 'Book me a flight to Boston' by actually purchasing a ticket. The model becomes a coordinator: it understands the question, knows which tools to use, chains them together, and synthesizes the answer from live results.

What breaks without it?

The model becomes stuck with only information from its training period. It cannot answer questions about events after training ended. It cannot check if a fact is correct (it just guesses). It cannot perform actions in the real world (sending messages, moving objects, updating records). A coding assistant cannot run the code to test if it works. A research agent cannot access papers published last month. A banking agent cannot check actual account balances. Every answer is a prediction based on old examples, not a result grounded in current reality.

Naive Starting Point

A beginner sees the problem and thinks: I can train the model on more data to make it smarter, or I can hardcode a separate set of rules for each tool—an if-then-if-then chain for 'fetch weather,' another for 'search the web,' another for 'send email.'

Why the Simple Approach Fails

Hardcoding rules fails because real-world tasks are infinite and intertwine in messy ways. The task 'fetch weather for a city' first needs to extract a city name, which might be hidden in an earlier part of the conversation or phrased ambiguously. The rule engine becomes thousands of if-then statements, still misses edge cases, and breaks when a new task arrives. It is brittle: it does not learn from mistakes and does not adapt when the world changes.

The Mathematical Object

You can represent the agent loop as a table or list of records. Each record holds: (state, action, observation). The state is the running text transcript, including previous results. The action is a choice from a fixed set: 'call search API', 'run Python code', 'query the database', 'respond to user'. The observation is the text result from that tool. You can inspect this sequence step by step, see where a decision went wrong, count how many steps it took, and measure how much information from past steps the model actually used.

The Operation

Start with the user's question as the initial state. The model reads the state and outputs the name of a tool and an input string for that tool. Execute the tool and add its result to the state. Loop: read the longer state, output the next tool and its input, execute it, extend the state. Continue until the model outputs a final answer text instead of a tool name. At that point, the loop stops and the user receives the answer.

Worked Mini-Example

User asks: 'What is the highest-grossing film of 2025?' Step 1: State is just the question. Model outputs action 'search for highest-grossing 2025 films'. Tool result: 'Top hits: Dune Messiah $1.9B, Avatar 4 $1.8B, Oppenheimer 2 $1.6B.' Step 2: State now holds the question and search results. Model outputs 'fetch box office details for Dune Messiah'. Tool result: 'Dune Messiah: $1.9B worldwide, $800M domestic.' Step 3: State includes the question and two tool results. Model outputs the final answer: 'Dune Messiah, with $1.9B worldwide.' The loop stops because the model produced an answer, not a tool request.

What the Lectures Emphasize

The Stanford CME295 agentic systems lecture frames a shift from a model running alone to a model embedded in a system. Before: the model sits by itself and predicts text. Now: the model sits inside a loop, connected to search engines, APIs, databases, and code interpreters. It does not need to be bigger or trained longer. It needs a new architecture—a circuit that calls tools and processes their results. This is the move from isolated prediction to closed-loop interaction with the world.

Common Misunderstanding

People think an agent is a bigger, smarter model or a fancier prompt. The real change is architecture, not size. The model is placed inside a loop, not used as a single black box. Instead of predicting everything at once, the model predicts one action, sees the result, and predicts the next action. This loop creates new failure modes: the tool might return wrong information, the model might misuse a tool, it might hallucinate a tool that does not exist, or errors might cascade (a wrong search result feeds into the next tool call, which feeds into the next). A simple bigger model never faced these problems.

How to Recognize This in a New Paper or Model

In papers, blog posts, or systems, watch for this closed-loop pattern: the model makes a decision, an external system runs, new information returns to the model, and the model decides again. You will see it called 'agent', 'retrieval-augmented generation' (or RAG), 'tool-using model', 'agentic loop', or 'environment interaction'. They are all describing the same core mechanism: a model that observes, acts, collects results, and updates its understanding repeatedly.

Connected Concepts

In Deep Reinforcement Learning (CS224R), an agent observes the state of the world, chooses an action, and receives a reward score—then uses the reward to learn better actions. Here, the model observes the state of a task, chooses a tool to call, and receives information as the 'reward'. In Image Diffusion (CME296), sampling is a loop where a noisy image is refined step by step, observing the current image and deciding how to denoise. In Robotics (CS223A), a robot observes sensor readings, chooses motor commands, and receives new sensor readings. The pattern—observe, act, receive feedback, decide again—appears throughout AI, whether generating language, images, robot motion, or text-based reasoning.
