Tokenization

Taking text and chopping it into numbered pieces so a computer can work with it. The computer reads these piece-numbers one at a time and learns patterns from them.

What real-world problem is this about?

Imagine you want to teach someone English using flashcards, but they can only handle 10,000 different cards at once. If you make one card for every letter, they'll never learn the rules for combining them. If you make one card for every possible word ever written, you'll need 500,000 cards and they'll still fail on words they've never seen. You need cards that are reusable: small enough to cover everything, large enough that patterns emerge quickly.

Why does this problem exist?

A computer can't read text the way your eyes do—it needs numbers. Text is infinite: new words, names, spellings show up all the time. So you pick a fixed list of chunks (usually 30,000–50,000 items) that act like LEGO bricks: you can build any sentence by stacking them. This list is called your tokenizer.

What is the mathematical idea underneath?

A tokenizer is a table that maps each chunk of text to a number. 'Hello' might be number 42, 'world' might be 999. When you write 'hello world', the tokenizer turns it into [42, 999]. The trick is choosing smart chunks. Modern tokenizers use subword pieces: they find chunks that repeat across different words. The word 'unbelievably' becomes ['un', 'believ', 'able', 'ly'], maybe numbers [201, 456, 78, 23]. The piece 201 ('un') also appears in 'unable' and 'unlock', so the model learns that 'un' means the same thing in all three words. This reuse is the secret.

Why is this concept important?

The tokenizer decides how many different pieces the model needs to learn and how long each sentence becomes when written as numbers. Good tokenization makes rare words, numbers, and code into a few pieces each. Bad tokenization explodes them into many pieces, wasting the model's memory and slowing it down.

What breaks without it?

Without a tokenizer, the model would receive raw text or random bytes with no consistent structure. Every sentence would look different—the model would have nothing stable to learn from.

Naive Starting Point

A beginner might think: use single letters as pieces. Or use whole words. Both sound simple.

Why the Simple Approach Fails

Single-letter pieces make sentences way too long: 'transformers' becomes 11 pieces. The model wastes memory on spelling details and can't spot word-level patterns. Whole-word pieces fail whenever you see a word you didn't train on—the model crashes because it has no token for it. Subword pieces solve both problems: they keep sequences short and handle any word by splitting it into recognized parts.

The Mathematical Object

The tokenizer is a lookup table: text pieces → numbers. Modern tokenizers build this table from training data using algorithms like byte-pair encoding, which finds the most useful chunk-pairs to combine. You can inspect it: look up number 1024 and see it represents the piece 'ing'; look up 58 and see it represents 'the'. It's a real, editable list you can shrink to save memory or expand to add a new language.

The Operation

Scan the text left to right. Find the longest chunk that matches an entry in your vocabulary table. Write down its number. Move forward and repeat. Example: 'playful' matches 'play' (one chunk) and then 'ful' (one chunk), so it becomes two numbers.

Worked Mini-Example

Take the sentence 'I love transformers code.' The byte-pair encoding tokenizer, trained on 1 billion English documents, maintains a vocabulary of 50,000 pieces. It reads left-to-right: 'I' matches token 1 (ID 1, a single character piece), 'love' matches token 2 (ID 5042, a whole word piece), 'transformers' does not exist as a single token, so it splits into 'trans' (ID 12847) and 'form' (ID 9234) and 'ers' (ID 3891), 'code' matches token 3 (ID 2908), '.' matches token 4 (ID 13). The model receives the vector [1, 5042, 12847, 9234, 3891, 2908, 13], which is 7 tokens long. With a character-level tokenizer (26 tokens for a-z plus punctuation), the same sentence becomes [9, 0, 12, 15, 22, 5, 20, 0, 25, 18, 1, 14, 19, 6, 15, 18, 13, 11, 5, 18, 19, 0, 3, 15, 4, 5, 0, 0, 0] (about 30 tokens), wasting memory and preventing the model from learning word-level patterns. With a whole-word tokenizer, 'transformers' would need to be in the vocabulary to avoid crashing on unknown words. The subword approach compresses the sequence by 4× while handling any word through recognized parts.

What the Lectures Emphasize

CME295 treats tokenization as the first step everything else depends on. Before the model can process text, it must convert it to a number-list. The lecture stresses: your tokenizer choice cascades forward. It decides what counts as a single unit in the model's eyes, how it handles rare or new words, and how many steps long each sentence becomes. Wrong tokenization early on breaks everything downstream.

Common Misunderstanding

Many students see tokenization as boring plumbing—just a technical detail before the real work. But it's not. Tokenization is the model's alphabet. A poor tokenizer might turn a smiley face into five numbers, a web address into a hundred numbers, or a variable name into three numbers, all wasting the model's working memory.

How to Recognize This in a New Paper or Model

In papers on vision models, you'll read 'the image is divided into 16×16 patches'—that's tokenization for pictures. In speech models, 'the audio is converted into sound-feature-snapshots'—that's tokenization for sound. The idea is always the same: take continuous or messy input and convert it into a fixed set of reusable pieces.

Connected Concepts

In CME296 (images and diffusion), visual tokenization works the same way: images are chopped into small squares before processing. In deep RL courses, when you split a dial's range into bins, you're tokenizing continuous values into discrete pieces. Across all three courses, tokenization is the same job: shrink the input so the model can learn faster while keeping everything that matters.
