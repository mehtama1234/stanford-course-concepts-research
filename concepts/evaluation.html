Evaluation

A systematic test that shows what an AI system can actually do — and where it breaks — across many different kinds of inputs and situations.

What real-world problem is this about?

You hire a tutor for your child's math. The tutor solves every problem from the textbook perfectly. Then your child takes a real test with problems the tutor has never seen, and scores poorly. The tutor had memorized the specific problems, not understood the underlying math. You needed tests that covered the full range of real situations, not just the narrow textbook.

Why does this problem exist?

Claims about what a system can do are just words until you test them against real situations. If you only watch the system handle cases you picked, you see a distorted picture — like judging a weatherman's skill by only testing him on sunny days. You must design tests that probe the places where failures are most likely. This forces you to ask hard questions: What does success actually mean? What are the edge cases where things break?

What is the mathematical idea underneath?

A metric is a formula that takes outputs (what the model produces) and turns them into numbers or tables you can compare. For example, accuracy counts how many answers are right: accuracy = (number of correct answers) / (total answers). But one number throws away important details. A chatbot might score 85% on math questions but completely fail on logic puzzles; accuracy alone hides this difference. Better metrics split the score by type — one table for math, one for writing, one for reasoning. The truth: every number you report means you have deleted other information, and what you deleted is often as important as what you kept.

Why is this concept important?

Evaluation decides which systems get shipped to real users, which research gets funded, and which bugs stay hidden in production. A model that sounds convincing but invents false citations will erode trust. A translation tool that handles news articles well but stumbles on technical manuals will frustrate users. Without careful testing, teams optimize for a score rather than for real, useful capability.

What breaks without it?

Without structured testing, claims stay as anecdotes. One person tries a model and gets great output; another tries it and gets garbage. Both could be telling the truth — there is no way to know because you never defined what you are measuring or how broadly you would test. You cannot verify progress; a model might score high because it memorized the test examples, not because it learned something that works on new inputs.

Naive Starting Point

A beginner might think: just run the model once and see if the output looks good. If one output is right, the model is right. This avoids all the hard work of designing careful tests.

Why the Simple Approach Fails

One run tells you almost nothing. Show a model one example and it might produce a perfect answer by pure luck, because it memorized that exact case during training, or because the task is trivial. Run it on ten examples and you still do not know how it will perform on examples it has never seen before. The moment your inputs get diverse — different phrasings, edge cases, tricky adversarial inputs — a single good impression falls apart. You need systematic, broad coverage to catch where the model actually fails.

The Mathematical Object

The concrete things you build and inspect are: test sets (labeled examples the model did not see during training), metrics (formulas that score outputs), and tables (organized records showing scores across different conditions). A test set for a chatbot might contain 500 questions split into categories: math, writing, reasoning, factuality. A metric for image generation might measure two things: pixel-level quality (does the image look sharp and clear?) and semantic match (does the image match the prompt?). These are real, you can write them down, and you can modify them to probe deeper.

The Operation

First, decide what counts as success for this system. Write down specific test cases that cover all the kinds of inputs you care about. Second, run your model on all these cases and record the outputs. Third, score each output using your metric — count correct answers, measure how similar it is to the ideal answer, or have people judge the quality. Fourth, combine all the scores into a summary: total accuracy, breakdown by category, how errors are distributed. Fifth, look at where scores drop; those are your failure modes.

Worked Mini-Example

Two language models report strong performance on a single-number benchmark (both score above 85% on a generic language task). You build a fine-grained test set with 600 examples split into six categories (math: 100 examples, reasoning chains: 100, factuality: 100, writing quality: 100, code: 100, common-sense: 100). Model A scores: math 94%, reasoning 89%, factuality 72%, writing 91%, code 88%, common-sense 86% (weighted average: 87%). Model B scores: math 78%, reasoning 91%, factuality 91%, writing 80%, code 92%, common-sense 85% (weighted average: 86%). A single-number comparison ('Model A beats Model B by 1%') hides opposite failure modes. Model A excels at arithmetic but hallucinates facts (72% on factuality means 28% of its factual claims are invented). Model B struggles with math problems but is reliable for real information. For a customer-support chatbot, factuality matters more than math; Model B is preferable. For homework help, Model A is better. Structured evaluation exposes these trade-offs so you choose the model that fails acceptably for your actual use case.

What the Lectures Emphasize

Stanford's courses treat testing as the core tool for improving AI systems. CME295 (Transformers) emphasizes that without measuring how language models perform on different tasks — chatbots that reason, search-and-answer systems, step-by-step reasoning — you have no signal for improvement. CME296 (Images and Diffusion) separates image quality (does it look good?) from prompt adherence (does it match what you asked for?); an image can look beautiful but ignore your prompt, or follow your prompt perfectly but look blurry. CS224R (Deep Reinforcement Learning) treats testing a deployed policy in the real world as a distinct challenge — testing behavior that was learned in a simulator differs from testing it when robots interact with actual physics. The shared thread: testing is not one score but a full set of probes aimed at different failure modes.

Common Misunderstanding

People often treat a benchmark score as the final truth about what a system can do. They think: Model X scored 85% on this test, so it is 85% capable. This ignores that a score is a snapshot under specific test rules. The test might miss distribution shift (the model trained on 2020 data but you use it on 2024 data), adversarial examples (unusual inputs designed to break it), or whole categories the test never examined. A model can score high on a benchmark and fail in the real world because the real world includes cases the benchmark did not sample.

How to Recognize This in a New Paper or Model

In a new paper or system, watch for testing whenever you see authors turn model outputs into scored numbers or benchmarks, collect human judgments, break down results by failure mode, or run ablation tests (remove a part and see what breaks). The common thread is always the same: design a test, measure systematically, interpret what you learn. You might see different names — 'benchmark,' 'test set,' 'human evaluation,' 'failure analysis,' 'ablation study' — but the core pattern never changes: measurement always reveals something and hides something else.

Connected Concepts

Testing runs through all three Stanford courses. In Transformers (CME295), you test how well an agent reasons and how well search-and-answer systems retrieve information. In Deep Reinforcement Learning (CS224R), you test whether a learned behavior actually works when deployed in the real world. In Diffusion and Vision (CME296), you test both how good the generated images look and how well they match the prompt. Testing also connects to generalization (does a model work on held-out examples it never trained on?) and scaling (does performance improve smoothly when you add more data or compute power?). The pattern holds everywhere: whenever you need feedback to know if you are making progress, testing is your tool.
