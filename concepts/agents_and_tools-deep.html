Agents and Tools — how wrapping a model in external checks turns guessing into certainty

A language model is a fluent guesser. It predicts plausible next words, which works beautifully for prose and explanation, but plausible is not exact. Ask it to count the letter 'r' in the word 'strawberry' and it guesses. Give it an arithmetic problem and it calculates in its head — unreliably. Here is the problem and the reframe: do not force the model to do every operation in its head; instead, turn it into an agent that can call external tools (a calculator, code, a search, a spell-checker) and verify its own work in a loop. The model becomes great at deciding what to compute and understanding the result, while the tools supply the exactness the model lacks. Here is the idea, a measurement on a real small model showing what happens when it checks its work, why offloading to tools works, where agents strain, and where this idea is reshaping applied AI.

1 · The problem — language models guess, and guessing fails on exactness

A language model works by predicting the next word from everything that came before. That prediction happens word by word, step by step, always betting on the most likely continuation. For writing, summarizing, and explanation, this is powerful — it captures grammar, tone, and reasoning. But the same mechanism that makes it fluent makes it brittle at tasks that demand exactness.

Count the letter 'r' in the word 'strawberry' — do it silently. A language model trying this in its head (answering cold, without intermediate steps) often misses. Simple arithmetic — does 7 times 8 equal 56? — it may not reliably know. Look up today's exchange rate or the capital of a country that changed borders? The model cannot — it has no access to current facts, only to patterns in its training data from months or years ago. And when it is wrong, it has no way to know.

So the need is stark: how can you take a model that is fluent but unreliable and make it dependable enough for real work?

2 · The reframe — let the model decide what to do, then hand the exactness to tools

The shift. Stop asking the model to do everything in its head. Instead, give it access to external tools — a calculator for arithmetic, code for computation, a search engine for current facts, a spell-checker to verify spelling, a code interpreter to try ideas. The model becomes an orchestrator: it reads the problem, decides what tool to use, calls the tool, reads the result, and checks whether the result makes sense. The loop is: think (model), act (tool), evaluate (model), revise if needed. The model is still fluent, still deciding; the tool is still exact and verifiable.

This pairing — a language model wrapped in a decision loop and linked to tools — is called an agent. The model is great at language and logic; the tools are exact. Together, the model supplies judgment and the tools supply certainty. The model decides when to call which tool; the tool does the calculation and the model reads and trusts the result because calculations never lie.

3 · Seen on a real run — the model is wrong cold but right when it checks

We tested a small language model (Qwen3, 0.6 billion parameters) on grade-school math problems from the GSM8K dataset. The question: does external checking actually help, and by how much? We measured what happens when the model answers a question cold (no intermediate steps, no checking) versus when it thinks first (breaks the problem into steps) and when it refines its answer (checks and revises, in a loop).

To show the core failure: the small model was asked 'How many times does the letter r appear in the word strawberry?' When answering cold (without thinking steps), it replied '1' — plainly wrong, and used 21 tokens. When it thinks first ('Let me spell it out: s-t-r-a-w-b-e-r-r-y...'), it counts correctly and answers '3' — correct — though it needs 336 tokens to be sure. The difference is not smarter reasoning; it is that verifying by going step by step catches errors the model would make in a fluent stream.

The discovered fact: a self-refine loop — where the model checks its own work and revises over two rounds — lifts accuracy from 42% to 58%, fixing 2 mistakes and breaking none. The model on its own gets hard problems wrong. Given a loop to verify (even without external tools), it catches errors it made in its first guess. And when external tools (a calculator, a spelling check, a search) are added, the gains compound further — the model decides what to compute, the tool computes it exactly, and the model reads a result it can trust.

4 · Why tools fix what guessing misses

The reason is separation of concerns. A language model is built to predict likely continuations of text; that skill is orthogonal to doing arithmetic, looking up facts, or verifying spelling. When you ask a model to count letters or do long division in its head, you are asking it to use the same prediction machinery for something it was never optimized for — it can approximate, but not reliably. When you give it a calculator, a search, or a spell-checker, you are using the right tool for the job.

The second reason is verifiability. A calculation has a right answer; a search result can be checked; code can be run and its output observed. When the model reads 'the sum is 56' from a calculator, that number is a fact, not a guess. The model's job shrinks to the task it is actually good at: reading the result, understanding what it means, and deciding what to do next. If the result is wrong (a calculator fed bad input, for instance), the model can often spot that because the result does not fit with what it knows.

5 · The one real weakness — agents can loop without converging and pile on errors

The catch is that adding a loop does not automatically make everything right. An agent can call the wrong tool, misread a result, or loop without ever settling on an answer. If the model misunderstands the problem, the tool will dutifully compute the wrong thing and the model will read garbage in, garbage out. If a tool is misconfigured or gives a cryptic error, the model may not recover. And the longer the chain of steps — decide, act, evaluate, revise — the more places each step can go wrong. A single mistake early in the chain can mislead every subsequent step.

The model is also only as good as its tools. A calculator will fail on a problem phrased ambiguously. A search engine might not find the one fact that settles the question. And the model itself, though better at language than arithmetic, can still misunderstand a tool's output or ask the wrong question. Agents are powerful but fragile — they demand careful tool design, clear error handling, and honest monitoring of whether the loops are actually converging to right answers or just spinning.

6 · The surprise — agents are the new frontier of applied AI

This pattern — a model that calls tools and checks its own work — is reappearing in every ambitious AI application right now. A coding assistant that writes code then runs it to check does this. A research agent that searches for papers, reads them, and summarizes does this. The shift from 'ask the model to do it all in one pass' to 'give the model a loop and some tools' is becoming the standard recipe for turning a fluent model into a dependable worker.

Critically, this is not just about language models. Any unreliable component paired with a verifiable tool and a decision loop becomes more reliable. The pattern shows up in reinforcement learning for language models, where a reward loop replaces guessing; in evaluation, where multiple graders replace a single judge; and in fine-tuning workflows, where iterative correction replaces one-shot learning. The core insight — separate what the model is good at from what tools are good at, then wire them together in a loop — is becoming the master pattern of modern AI.

7 · Where it is used in practice — turning fluent models into reliable workers that verify their answers

Code assistants like those in major IDEs call a code interpreter to run and test generated functions, then revise if the run fails. Research agents search for papers, read them, and summarize findings by chaining search queries, document retrieval, and reading loops. Chatbots answering factual questions (what is the capital of a country, what happened today) call a search engine and cite results. A model writing complex arithmetic problems calls a calculator, gets the exact answer, and uses that result to construct an explanation.

The model reads a problem and decides which tool to use (or whether to answer directly). It calls the tool, reads the exact result back, and asks itself: does this answer make sense? If not, it revises and loops again. The model supplies judgment and reasoning; the tool supplies certainty and verifiability. A calculator never lies; a search engine returns facts the model could not know; code run in a sandbox shows exactly what happened. The model's role shrinks to orchestrating these tools and understanding their results.

Wrapping a fluent model in a verification loop and external tools turns it into something dependable enough for real work because it separates guessing (where models excel) from exactness (where tools excel).
