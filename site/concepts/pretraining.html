Pretraining

Learning broad patterns from massive amounts of unlabeled data before teaching the model to do anything specific.

What real-world problem is this about?

You want to teach someone a skill, but good instructors are rare and expensive. However, raw examples of the skill in action are everywhere—books, videos, conversations. Someone who reads thousands of books absorbs patterns long before being taught explicitly.

Why does this problem exist?

A learner faces two constraints: good labeled data is rare, but patterns in raw data are free. Any system smart enough to extract patterns from raw examples before seeing labeled ones will need less labeled data later. That's a practical necessity, not a choice.

What is the mathematical idea underneath?

The model learns by reducing a loss—a number that measures how wrong or surprised the model was about what came next. When you predict the next word in a sentence and it's wrong, the loss is high; when you're right, it's low. The model adjusts its internal knobs (weights) to make this number smaller. Mathematically, you compute the average loss over millions of examples, then use calculus to find which direction each knob should turn. The reason this works is that patterns in language show up repeatedly—if you practice predicting 'next word' across billions of examples, you absorb structure like grammar, facts, and reasoning shortcuts without anyone telling you what they are.

Why is this concept important?

Pretraining builds a foundation of broad competence. The model learns what's possible in the domain (language, images, video) before being tuned for a specific task. This reusable knowledge means downstream tuning can work with far less labeled data and learns faster.

What breaks without it?

Every new task would need its own large hand-labeled dataset. Models would memorize narrow task-specific behavior from scratch, unable to transfer learning across domains. You'd need vastly more labeled data and much more compute for each new application.

Naive Starting Point

A beginner might hope to solve this by writing rules (if noun then expect verb next), or by hand-crafting features. That works for a hundred examples but completely breaks on the messy complexity of real language or vision—too many exceptions, too many patterns to hand-engineer.

Why the Simple Approach Fails

Rule-based systems fail because language is far too irregular—every rule has exceptions. Hand-crafted features freeze what the system can learn—a human has to guess which patterns matter before seeing the data. The model has no way to discover novel patterns or adapt when the data shifts.

The Mathematical Object

The concrete object is the model's internal numbers, called weights or parameters—a massive table of numbers (billions for large models) that can be adjusted during training. Each weight contributes a tiny piece to the final prediction. The model reorganizes these numbers to minimize the loss, sculpting them to capture patterns in the data.

The Operation

Start with a model that has random initial weights. Feed it text or images from massive datasets, one example at a time. For each example, compute the loss—how wrong was the prediction. Use calculus to calculate which direction each weight should move to reduce that loss. Adjust all weights slightly in that direction. Repeat billions of times across different data until the loss stops dropping noticeably.

Worked Mini-Example

Imagine pretraining a language model on Wikipedia text. Show it 'The cat sat on the _____' and it guesses 'sky'. The loss is high because the next word is 'mat'. The model adjusts its weights to favor 'mat' over 'sky' in this context. After seeing millions of sentences where the pattern is 'noun sat on concrete-object', the weights gradually encode that pattern. By the end of pretraining, the model predicts next tokens well—it's a good autocompleter. But it hasn't been told what 'helpful' means yet. That comes in the next stage, called fine-tuning.

What the Lectures Emphasize

The lecture frames pretraining as the compute-heavy first stage that consumes massive text and code datasets to teach the model the structure of language. The result is a model that predicts the next token accurately—a strong autocompleter. The lecturer explicitly notes that pretraining alone does not create a helpful assistant; it creates knowledge without alignment. That distinction matters: pretraining builds competence, but later stages add direction.

Common Misunderstanding

Many people assume pretraining alone creates an AI assistant. The lecture corrects this: pretraining produces a model that knows language and code structure, but has no notion of being helpful, honest, or harmless. Without fine-tuning toward preferred behavior, the model autocompletes whatever patterns it saw—which may be wrong, biased, or harmful. Pretraining is preparation, not the final product.

How to Recognize This in a New Paper or Model

Look for pretraining whenever a paper or system describes a model learning from abundant raw data through a general prediction task—next-token prediction, masked language prediction (guessing hidden words in a sentence), image-to-image denoising, contrastive learning (learning similarity between examples without labels), or self-supervised reconstruction. The common thread is practice from cheap, abundant feedback before specialization.

Connected Concepts

In CME295 (Transformers/LLMs), pretraining is the foundation before fine-tuning. In CME296 (Diffusion/Vision), the same pattern appears as diffusion models learning to denoise images from pure random noise before being conditioned for a specific task. In CS224R (Deep RL), agents explore and practice on reward-free environments before being shaped toward a goal. Across all three, the principle is: practice on abundant raw signal first, then direct the learned competence toward specific behavior.
