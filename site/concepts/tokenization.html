Tokenization

Converting text into a list of numbered pieces that a machine can process.

What real-world problem is this about?

Imagine you want to teach a foreigner English by showing them a book, but they can only learn 10,000 chunks at a time. If you teach them individual letters, they'll need to learn rules for combining them forever. If you teach them whole words, they'll trip over 'unbelievably' every time they see it because you taught them only 'believe'. You need chunks that reuse across words.

Why does this problem exist?

Computers cannot digest raw text the way you read it. They need to turn language into a sequence of numbers. But language is endless—new words, names, and spellings arrive constantly. So you must choose a fixed vocabulary (usually 30,000–50,000 items) that works as a universal building set. That vocabulary is your tokenizer.

What is the mathematical idea underneath?

A tokenizer is a lookup table: you map each possible chunk of text to an integer ID. For example, 'hello' might map to 42, 'world' to 999. When you feed the sentence 'hello world' to a transformer, it becomes the sequence [42, 999]. The genius is in choosing the chunks. Most modern tokenizers split text into subwords (morphemes and common pieces), so 'unbelievably' breaks into ['un', 'believ', 'able', 'ly']. Each piece gets an ID: maybe 201, 456, 78, 23. Now the model sees 'unbelievably' as [201, 456, 78, 23], and 'believe' becomes [456] plus context—the same piece 201 reappears in 'unable', 'unlock', etc.

Why is this concept important?

The tokenizer sets the model's effective vocabulary size and sequence length. Choosing tokens wisely makes rare words, numbers, and code easier for the model to learn. It also determines how long a sequence becomes: more fine-grained tokens mean longer sequences, which costs more memory and compute.

What breaks without it?

Without a tokenizer, the model receives a continuous stream of text or random bytes—no consistent units. Different sentences would have different 'shapes' each time, and the model would have nothing stable to learn patterns from.

Naive Starting Point

A beginner might think: just use letters as tokens. Or just use whole words. Both seem simple.

Why the Simple Approach Fails

Letter tokens make sequences too long: 'transformers' becomes 11 tokens. The model wastes context on spelling details. Whole-word tokens fail when you meet an unseen name or a misspelling—there's no token for it, so the model crashes. Subword tokenization solves both: short sequences and no out-of-vocabulary words.

The Mathematical Object

The tokenizer is a table of strings → integers. Modern tokenizers use a learned vocabulary built from training data (byte-pair encoding or WordPiece). You can inspect it: look up token 1024, see it's the piece 'ing', look up token 58, see it's 'the'. It's a concrete, modifiable artifact—you can shrink it to save memory or expand it to handle a new language.

The Operation

Take the input text, scan left to right, match the longest sequence of characters to an entry in your vocabulary table, record its ID, move forward, and repeat. For example: 'playful' scans as 'play' (one token), then 'ful' (one token) → two tokens total.

Worked Mini-Example

Sentence: 'I love Python code.' Tokenizer breaks it: 'I' → 1, 'love' → 5042, 'Python' → [1234, 8] (two subword tokens for a rare word), 'code' → 2908, '.' → 13. The model receives [1, 5042, 1234, 8, 2908, 13]. Notice 'Python' used two tokens (a root + a suffix-like piece), while common words use one. If the training data never saw 'Python', the tokenizer still handles it by splitting into components it recognizes.

What the Lectures Emphasize

CME295 frames tokenization as the essential first step: before a transformer can embed anything, it must convert text to atomic pieces. The lecture stresses that this choice cascades—your tokenizer determines what the model sees as a single unit, how it breaks rare words, and how long your sequence becomes. Get tokenization wrong, and everything downstream struggles.

Common Misunderstanding

Students often think tokenization is a boring plumbing step that doesn't matter. In reality, tokenization defines the model's alphabet. Poor tokenization can force the model to see an emoji as five tokens, a URL as a hundred pieces, or a code variable as three fragments—wasting context and slowing learning.

How to Recognize This in a New Paper or Model

In a paper about vision transformers, you'll see 'the image is divided into 16×16 patches'—that's tokenization for images. In a speech model, 'mel-spectrogram frames are converted to discrete codes'—that's tokenization too. The principle is always the same: convert continuous or variable-length input into a fixed inventory of reusable units.

Connected Concepts

In CME296 (diffusion/vision), visual tokenization (ViT patches) follows the same logic: cutting images into overlapping squares before embedding. In deep RL (CS224R), when you discretize continuous action spaces into 'bins', you're tokenizing actions. Across all three courses, tokenization is compression at the interface: choose what to keep, ensuring both coverage and efficiency.
