Big Picture From First Principles

Start with one ordinary fact: text is a chain of pieces, and each piece gets its meaning from other pieces around it. Transformers and LLMs are built around that fact. The model turns text into tokens, turns tokens into vectors, lets vectors compare with each other, trains on prediction, then gets tuned and tested for useful behavior.

The course keeps rebuilding one pipeline: represent the text, mix context with attention, train the model to predict, tune the model toward desired answers, extend it with reasoning or tools, and evaluate whether it actually works.

Text Needs Pieces

Tokenization decides the units the model can see and predict.

Pieces Need Numbers

Embeddings turn tokens into vectors that can be compared and changed.

Context Changes Meaning

Attention lets each token pull information from other tokens.

Order Must Be Added

Position information tells the model where each token sits.

Prediction Teaches Patterns

Next-token pretraining teaches grammar, facts, style, and code structure at scale.

Tuning Shapes Behavior

Fine-tuning and preference training turn a predictor into a more useful assistant.

Tools Extend The Model

Retrieval and tool calls let the system use outside information and actions.

Scores Are Partial

Evaluation must check correctness, usefulness, safety, cost, and failure cases.

Lecture 1

Lecture 1 - Transformer

Open video

1h 41m · 12891 transcript words

Detailed Topic Explanation

The transformer solves a basic reading problem. A model receives a line of tokens and must decide which earlier or nearby tokens matter for understanding each token. Older sequence models read mostly step by step, which made long-range links hard to carry. Attention changes the operation: each token can compare itself with other tokens and pull in the information it needs. This makes the model less like a single narrow memory and more like a table where every token can look across the table.

The central object is not a word but a vector, a list of numbers representing a token. Attention builds three views of each token: a query that asks what it needs, a key that says what it offers, and a value that contains the information to pass along. Matching queries to keys gives weights. Those weights mix values. A transformer block repeats this with several heads, then uses a feed-forward network and normalization to update the token vectors. The result is a system that can build context-sensitive meanings from the whole sequence.

Core Ideas

  • Tokens must be turned into vectors before the model can compare or update them.
  • Self-attention lets each token decide which other tokens matter for its current meaning.
  • Queries, keys, and values separate asking, matching, and carrying information.
  • Transformer blocks stack attention, feed-forward updates, residual paths, and normalization.

Approaches Taught

Self-attention

Problem
Each token needs information from other tokens in the same sequence.
How It Works
Compute query, key, and value vectors, use query-key matches to weight value vectors, and mix the information back into each token.
Why It Matters
It lets the model build context-sensitive token meanings instead of reading with one narrow memory.
Where It Breaks
Attention can be expensive for long contexts and can focus on misleading tokens.

Transformer block stacking

Problem
One attention pass is not enough to build rich language representations.
How It Works
Repeat attention, feed-forward updates, residual paths, and normalization across many layers so each layer refines the token vectors produced by earlier layers.
Why It Matters
Stacking lets later layers build more abstract features from earlier token relations.
Where It Breaks
Deep stacks become unstable or expensive without careful normalization and residual design.

Examples Used

  • In 'the animal did not cross the street because it was tired', attention helps decide what 'it' refers to.
  • A token for 'bank' can mean a financial place or river edge depending on nearby tokens.
  • A long document can contain a relevant fact many tokens before the answer.

Equations And Algorithm Moves

  • Map each token id to an embedding vector.
  • Compute Q, K, and V vectors from each token vector.
  • Score token pairs with QK^T, scale the scores, and apply softmax.
  • Use the attention weights to mix V vectors.
  • Apply feed-forward layers, residual connections, and normalization.

What You Should Be Able To Say

You should be able to explain a transformer as a stack of blocks where each token repeatedly looks at other tokens and updates its vector.

Lecture 2

Lecture 2 - Transformer-Based Models & Tricks

Open video

1h 47m · 12914 transcript words

Detailed Topic Explanation

Transformer tricks exist because the simple attention idea is not enough by itself. If a model only sees a bag of token vectors, it may know which words appear but not their order. Position encodings add location information so 'dog bites man' differs from 'man bites dog.' Other design choices make training stable and efficient: masking prevents future-token leakage, multi-head attention lets the model compare tokens in several ways, and normalization keeps activations from drifting too far.

The first-principles question is what information the block must preserve. It needs content, order, causality, and stable signal size. Content comes from embeddings. Order comes from position encodings. Causality comes from masks when the model predicts the next token. Multiple heads let the model track different relations at once, such as grammar, reference, and topic. Residual connections protect earlier information from being overwritten. These are not cosmetic tricks; each one fixes a specific failure in the plain attention setup.

Core Ideas

  • Position encodings add order information that self-attention does not naturally contain.
  • Causal masks stop the model from seeing future tokens during next-token training.
  • Multi-head attention lets different heads track different relationships.
  • Residual paths and normalization keep deep transformer stacks trainable.

Approaches Taught

Positional encoding

Problem
Plain attention does not know token order.
How It Works
Add or combine position information with token embeddings before attention layers process them.
Why It Matters
It lets the model distinguish sequences with the same words in different orders.
Where It Breaks
Poor position handling can break long-context behavior or confuse order-sensitive tasks.

Causal masking

Problem
A next-token model must not see future answer tokens during training.
How It Works
Block attention from each token to later tokens by masking future attention scores.
Why It Matters
It keeps the training task honest and matches generation, where future tokens are unknown.
Where It Breaks
Wrong masks leak answers or prevent the model from using valid context.

Examples Used

  • The same words in a different order can mean the opposite thing.
  • A next-token model should not peek at the answer token during training.
  • One attention head may track subject-verb relation while another tracks topic words.

Equations And Algorithm Moves

  • Add or combine positional vectors with token embeddings.
  • Apply a mask that sets illegal future attention scores to a very negative value.
  • Run several attention heads in parallel and concatenate their outputs.
  • Use residual addition so each layer updates rather than replaces the representation.
  • Use layer normalization to keep vector scale manageable.

What You Should Be Able To Say

You should be able to explain why transformers need order, masks, multiple heads, residuals, and normalization to become usable language models.

Lecture 3

Lecture 3 - Tranformers & Large Language Models

Open video

1h 48m · 13345 transcript words

Detailed Topic Explanation

Large language models begin with a simple training game: predict missing or next tokens from context. The game is simple, but the data is huge. Tokenization cuts text into units. Embeddings turn those units into vectors. Transformer layers update the vectors using context. The output head turns the final vector into probabilities over possible next tokens. Repeating this over massive text teaches the model many patterns because good prediction requires grammar, world facts, style, code structure, and task habits.

The key is that next-token prediction is not only about the next word. To predict well, the model must compress useful information about what came before. It must track syntax, topic, names, references, and common reasoning patterns. The model does not store a database in a clean symbolic form. It stores many statistical regularities in its weights. This explains both strength and weakness: it can generalize patterns broadly, but it can also invent plausible text when the needed fact is absent or uncertain.

Core Ideas

  • Tokenization defines the pieces the model can directly predict.
  • Pretraining uses a broad prediction task to learn many language patterns at once.
  • The output is a probability distribution over next tokens, not a guaranteed fact.
  • Scale helps because more data and parameters let the model store and combine more patterns.

Approaches Taught

Next-token pretraining

Problem
The model needs a broad signal that can be created from raw text at scale.
How It Works
Train the model to predict the next token from previous context across a very large corpus.
Why It Matters
Good prediction forces the model to learn grammar, facts, style, code patterns, and common reasoning habits.
Where It Breaks
Predicting likely text can produce fluent falsehoods and does not guarantee helpful behavior.

Token-to-logit pipeline

Problem
Text must become model input and model output in a computable form.
How It Works
Tokenize text, embed token ids, process vectors through transformer blocks, and project final vectors to vocabulary logits.
Why It Matters
It is the basic mechanism behind modern LLM training and generation.
Where It Breaks
Tokenizer choices, context limits, or bad probability calibration can damage output quality.

Examples Used

  • After 'The capital of France is', the model should put high probability on 'Paris'.
  • In code, indentation and prior function names shape the next-token prediction.
  • A rare factual question may produce a fluent but wrong answer if the pattern is weak.

Equations And Algorithm Moves

  • Tokenize text into ids.
  • Map ids to embeddings and add position information.
  • Run transformer blocks over the context.
  • Project final vectors to vocabulary logits.
  • Train with cross-entropy loss against the true next token.

What You Should Be Able To Say

You should be able to explain pretraining as massive next-token prediction that forces the model to learn useful text patterns, while still producing probabilities rather than truth guarantees.

Lecture 4

Lecture 4 - LLM Training

Open video

1h 47m · 13926 transcript words

Detailed Topic Explanation

LLM training turns the next-token game into a large engineering system. The basic update is clear: predict tokens, measure loss, change weights. The hard part is doing that at scale without wasting compute or corrupting the signal. Data must be cleaned and mixed. Batches must feed hardware efficiently. Learning rates must change over time. Validation must show whether the model is learning patterns that transfer, not only memorizing training text. Scaling choices decide how much data, compute, and parameter count to use.

The first-principles issue is that every training token is a lesson. Bad data teaches bad habits. Duplicate data can make memorization easier. Poor mixing can overfit the model to one style or domain. Too large a learning rate can destroy progress; too small can waste compute. Mixture-of-experts and related scaling ideas try to increase capacity without activating every parameter on every token. The goal is not only low loss but useful behavior after training, which means the training system must be measured carefully.

Core Ideas

  • The training loop is prediction, loss measurement, gradient update, and validation.
  • Data quality and data mix shape the model as much as architecture does.
  • Scaling requires tradeoffs among parameters, tokens, compute, and inference cost.
  • Validation and test sets are needed because training loss can hide memorization or weak transfer.

Approaches Taught

Large-scale pretraining system

Problem
A useful LLM requires huge amounts of data and compute without unstable optimization.
How It Works
Feed curated token batches through the model, compute cross-entropy loss, backpropagate gradients, and validate on held-out data.
Why It Matters
It turns the simple prediction task into a reliable training process at scale.
Where It Breaks
Bad data, bad schedules, duplicates, or poor validation can waste compute or teach bad behavior.

Efficient scaling

Problem
More capability usually costs more training and inference compute.
How It Works
Use scaling choices, routing, or sparse activation so capacity grows without activating every parameter for every token.
Why It Matters
It makes larger models more practical to train or serve.
Where It Breaks
Efficiency tricks can add routing errors, uneven expert use, or difficult system complexity.

Examples Used

  • A model trained on messy web text may learn toxic, duplicated, or low-quality patterns.
  • A validation split catches cases where training loss improves but unseen examples do not.
  • Mixture-of-experts can route a token to a subset of parameters instead of using the whole model.

Equations And Algorithm Moves

  • Sample token batches from a curated data mixture.
  • Compute next-token cross-entropy loss.
  • Backpropagate gradients through transformer weights.
  • Update weights with an optimizer and learning-rate schedule.
  • Track training, validation, and held-out performance.

What You Should Be Able To Say

You should be able to explain LLM training as a scaled prediction system where data, optimization, validation, and compute choices decide what the model actually learns.

Lecture 5

Lecture 5 - LLM tuning

Open video

1h 47m · 13228 transcript words

Detailed Topic Explanation

Tuning changes a base model into a more useful assistant. Pretraining teaches broad language ability. Supervised fine-tuning teaches the model to answer in desired formats using examples. Preference tuning then uses comparisons between answers to push the model toward responses people prefer. The core idea is that predicting internet text is not the same as serving a user. A useful assistant needs extra training signals that describe the desired behavior. Those signals tell the model how to respond when several fluent completions are possible but only some are helpful, honest, or safe.

The first-principles split is between knowledge and behavior. Pretraining gives many patterns, but it does not define what answer style, refusal behavior, detail level, or safety policy is preferred. Fine-tuning supplies direct demonstrations. Preference tuning supplies relative judgment: answer A is better than answer B. Reward models, RL-style tuning, and direct preference objectives are different ways to turn those comparisons into weight updates. The failure mode is optimizing the proxy instead of the real user need: a model can become verbose, evasive, flattering, or reward-hacking.

Core Ideas

  • Pretraining gives broad capability but not necessarily desired assistant behavior.
  • Supervised fine-tuning teaches by demonstration.
  • Preference tuning teaches from comparisons between possible answers.
  • A learned preference signal can be useful but can also be gamed.

Approaches Taught

Supervised fine-tuning

Problem
A pretrained model may not answer in the desired format or style.
How It Works
Train on prompt-response examples that demonstrate the wanted behavior, so the model learns how instructions should map to complete answers.
Why It Matters
It teaches instruction following more directly than raw next-token pretraining.
Where It Breaks
The model can overfit the examples or inherit narrow demonstration habits.

Preference tuning

Problem
Many answer qualities are easier to compare than to write as exact labels.
How It Works
Collect chosen/rejected answer pairs and update the model through a reward model, RL objective, or direct preference loss.
Why It Matters
It moves the model toward answers people judge better after it already knows language.
Where It Breaks
The preference signal can reward style over truth or be gamed by the model.

Examples Used

  • A base model may continue a prompt instead of answering it helpfully.
  • A preference label may choose the clearer of two answers to the same question.
  • A tuned model can over-refuse if safety examples dominate too bluntly.

Equations And Algorithm Moves

  • Start from a pretrained model.
  • Fine-tune on prompt-response demonstrations.
  • Collect chosen and rejected answers for the same prompt.
  • Train a reward model or direct preference objective from those pairs.
  • Update the language policy while limiting harmful drift from the base model.

What You Should Be Able To Say

You should be able to explain tuning as the extra training that turns a text predictor into a model that follows instructions and prefers better answers.

Lecture 6

Lecture 6 - LLM Reasoning

Open video

1h 47m · 13136 transcript words

Detailed Topic Explanation

LLM reasoning asks how to make a model handle problems where the answer depends on intermediate work. A normal model can emit a quick answer, but math, planning, code, and logic often need a chain of steps. A reasoning trace makes that chain visible. The model writes partial work, uses it as context, and then produces the answer. Training can reward final correctness, imitate good traces, or use process-level signals that judge intermediate steps. The main question is how to make the written steps improve the answer instead of merely making the answer look thoughtful.

The credit problem is the same one seen in RL. If the final answer is wrong, which earlier step caused the failure? If the final answer is right, which steps were actually necessary? Reasoning methods try to create better feedback by sampling several attempts, checking final answers, using verifiers, or scoring prefixes. The danger is that longer text is not automatically better reasoning. A trace can be fluent but wrong, circular, or padded. The useful target is not more words; it is steps that increase the chance of a correct answer.

Core Ideas

  • Reasoning traces make intermediate work visible to the model and evaluator.
  • Final-answer reward is sparse because it says little about individual steps.
  • Verifiers and process feedback try to judge partial solutions.
  • Longer reasoning can help or hurt depending on whether the steps are actually useful.

Approaches Taught

Reasoning traces

Problem
A final answer does not show the intermediate choices that produced it.
How It Works
Let the model generate intermediate written steps and use those steps as context before the final answer.
Why It Matters
It gives the model a workspace for multi-step tasks and exposes partial work for checking.
Where It Breaks
The trace can be long, fluent, and still wrong or unnecessary.

Verifier-guided reasoning

Problem
The model needs feedback about which attempted solutions are likely correct.
How It Works
Sample candidate traces or answers, score them with a verifier or final check, and train or select using that score.
Why It Matters
It can improve hard tasks where one sample is unreliable.
Where It Breaks
A weak verifier can reward shortcuts, superficial correctness, or overfit solution styles.

Examples Used

  • A math solution may fail because of one early algebra mistake.
  • A code answer may need planning, implementation, and testing steps.
  • Sampling several traces can find one correct solution even when many attempts fail.

Equations And Algorithm Moves

  • Represent a problem plus current written prefix as the state.
  • Generate the next reasoning step as the action.
  • Score final correctness or intermediate process quality.
  • Use successful traces, verifier scores, or preference signals to update the model.
  • Measure pass rate and robustness, not only trace length.

What You Should Be Able To Say

You should be able to explain reasoning training as learning which intermediate text steps make the final answer more likely to be correct.

Lecture 7

Lecture 7 - Agentic LLMs

Open video

1h 49m · 13821 transcript words

Detailed Topic Explanation

Agentic LLMs extend the model beyond one response. The model may retrieve documents, call tools, write code, inspect results, and decide what to do next. Retrieval adds outside knowledge by searching chunks of text using embeddings. Tool calling gives the model access to calculators, databases, browsers, code runners, or APIs. An agent loop lets the model observe, plan, act, observe again, and stop when the task is done. The shift is from answering from memory to controlling a small work process around the model.

The first-principles issue is that text prediction is not enough when the answer depends on fresh facts or external effects. A model's weights are fixed after training, so retrieval supplies current or private information. A model can describe arithmetic, but a calculator can compute it reliably. A model can suggest code, but a runtime can test it. The main risk is control: tool errors, bad retrieval, prompt injection, hidden assumptions, and endless loops can make an agent worse than a single careful answer.

Core Ideas

  • Retrieval gives the model external context that was not stored reliably in its weights.
  • Embeddings let the system search for chunks with similar meaning.
  • Tool calling lets the model delegate operations it should not do from memory.
  • Agent loops combine planning, action, observation, and stopping rules.

Approaches Taught

Retrieval-augmented generation

Problem
The model weights may not contain current, private, or exact information.
How It Works
Embed the query and documents, retrieve relevant chunks, and place them into the model context before answering.
Why It Matters
It gives the model grounded information without retraining the whole model.
Where It Breaks
Bad retrieval or prompt injection can make the answer worse than using no retrieval.

Tool-calling agent loop

Problem
Some tasks require actions outside text generation.
How It Works
Let the model choose structured tool calls, execute them, feed observations back, and repeat until done.
Why It Matters
It lets the system calculate, search, code, inspect, and update state.
Where It Breaks
The loop can call the wrong tool, trust bad outputs, leak data, or fail to stop.

Examples Used

  • A model retrieves a company policy document before answering an HR question.
  • A model calls a calculator instead of doing long arithmetic from memory.
  • A coding agent writes a test, runs it, reads the error, and edits the code.

Equations And Algorithm Moves

  • Embed the user query and document chunks into vectors.
  • Retrieve nearest chunks and place them into the context.
  • Let the model choose a tool call with structured arguments when needed.
  • Execute the tool and feed the observation back to the model.
  • Repeat until a stopping condition or final answer is reached.

What You Should Be Able To Say

You should be able to explain an agentic LLM as a model wrapped in retrieval, tools, observations, and control rules so it can work beyond one text reply.

Lecture 8

Lecture 8 - LLM Evaluation

Open video

1h 49m · 13617 transcript words

Detailed Topic Explanation

LLM evaluation asks what behavior should count as success. A model may answer one benchmark well and still fail real users. It may be fluent and wrong, safe and unhelpful, or helpful and unsafe. Evaluation therefore needs several kinds of tests: task accuracy, instruction following, factuality, reasoning, robustness, safety, bias, tool use, latency, cost, and human preference. The point is not to find one perfect metric. The point is to build enough evidence for the intended use.

The first-principles problem is mismatch between a score and the real goal. BLEU and ROUGE can help with translation or summarization but miss deeper usefulness. Multiple-choice benchmarks are scalable but can be memorized or overfit. Human ratings capture preference but are noisy and expensive. Agent tasks test real workflows but are harder to reproduce. Good evaluation slices the task: what user, what domain, what failure, what cost, what risk. Averages are dangerous because they hide rare failures that may matter most.

Core Ideas

  • Evaluation must match the use case, not just the model family.
  • Automatic metrics are scalable but incomplete.
  • Human preference is valuable but noisy and setup-dependent.
  • Safety, robustness, cost, and latency are part of real model quality.

Approaches Taught

Task-specific evaluation

Problem
A general benchmark may not measure the behavior a real use case needs.
How It Works
Define target tasks and failure modes, then measure accuracy, usefulness, safety, cost, and latency on those slices.
Why It Matters
It turns evaluation into evidence for a concrete deployment rather than a vanity score.
Where It Breaks
Bad slices or contaminated benchmarks can hide real regressions.

Human and preference evaluation

Problem
Some answer qualities are subjective or hard to capture with rules.
How It Works
Ask people or preference models to compare outputs on clarity, helpfulness, correctness, and policy fit.
Why It Matters
It captures aspects of user experience that automatic metrics miss.
Where It Breaks
Judgments can be noisy, biased, expensive, and sensitive to rubric wording.

Examples Used

  • A summarizer can score well on overlap metrics while omitting the key fact.
  • A model can pass a math benchmark if similar problems were in training data.
  • A support chatbot must be measured for correctness, helpfulness, refusal behavior, and escalation.

Equations And Algorithm Moves

  • Define the target behavior and failure modes before choosing metrics.
  • Use task-specific automatic scores where they are meaningful.
  • Run human or model-assisted preference checks for subjective quality.
  • Slice results by domain, difficulty, user group, safety category, and tool-use path.
  • Track regressions across model versions, not only headline averages.

What You Should Be Able To Say

You should be able to explain LLM evaluation as building evidence for a specific use case, because no single benchmark proves a model is good.

Detailed Topic Explanation

The recap and trends lecture ties the course together. The basic pipeline is still visible: tokenize text, embed tokens, add order, process with transformer blocks, pretrain on prediction, tune for desired behavior, add reasoning or tools when needed, and evaluate carefully. Current trends change pieces of that pipeline. Some change architecture or attention. Some change training data and scale. Some change post-training. Some add retrieval, tools, multimodal inputs, or agent loops. The practical habit is to stop reading new methods as names and start reading them as changes to one part of the pipeline.

The first-principles way to read trends is to ask which bottleneck is being attacked. Is the model too expensive? Then look for sparse activation, smaller models, distillation, or better inference. Does it lack fresh knowledge? Look for retrieval. Does it fail multi-step tasks? Look for reasoning, search, verification, or tool use. Does it fail evaluation? Look for better benchmarks and deployment tests. New names matter less than the pressure they respond to and the tradeoff they create.

Core Ideas

  • Most new LLM work changes representation, architecture, training, tuning, tools, reasoning, or evaluation.
  • A trend is easier to understand when tied to the bottleneck it tries to fix.
  • Multimodal and agentic systems reuse transformer ideas while adding new inputs and actions.
  • Every improvement has a tradeoff in cost, reliability, controllability, or evaluation.

Approaches Taught

Pipeline-based paper reading

Problem
New LLM papers can look unrelated because each names a different component.
How It Works
Locate the method in the pipeline: tokens, embeddings, attention, training objective, tuning, retrieval, tools, reasoning, or evaluation.
Why It Matters
It turns new trends into understandable modifications of known parts.
Where It Breaks
A method can change several parts at once, so oversimplifying the location can miss the real tradeoff.

Bottleneck-first analysis

Problem
Trends are hard to judge if they are read only as names or demos.
How It Works
Ask what bottleneck the method attacks, what object it introduces, and what failure mode remains.
Why It Matters
It keeps attention on mechanism and tradeoff instead of hype.
Where It Breaks
The stated bottleneck may differ from the real deployment bottleneck.

Examples Used

  • A retrieval system changes the knowledge bottleneck without retraining the whole model.
  • A sparse model changes inference cost by activating only part of the network.
  • A multimodal model reuses sequence processing but adds image or audio tokens.

Equations And Algorithm Moves

  • Locate the method inside the pipeline: tokenization, embedding, block, objective, tuning, tool loop, or evaluation.
  • Name the bottleneck it addresses.
  • Identify the new object it introduces, such as a routing rule, retriever, verifier, or multimodal encoder.
  • Ask how the object changes training or inference.
  • Check what failure mode or tradeoff remains.

What You Should Be Able To Say

You should be able to read a new LLM paper by locating which part of the pipeline it changes and what bottleneck it is trying to remove.
